Browser Workflow Tools for MCP

A workflow contract and execution model for exposing reviewed browser workflows as typed Model Context Protocol tools.

Normative source · Product specification · Build plan

What you are reading: This draft describes how a reviewed browser workflow can become one reusable, typed MCP tool. It is an early implementation-oriented proposal from the browser-to-mcp project, not a W3C Recommendation or MCP specification.

1. Introduction

Many useful business capabilities exist only behind a web user interface. Generic browser-control tools can operate those sites, but an agent must rediscover the same page structure on every run. This proposal turns a reviewed workflow into a narrow business tool.

workflow contract -> validate -> policy check -> replay -> typed result

2. Workflow contract

The canonical authoring format is YAML. Implementations parse it into typed models before serving or executing it. A workflow declares its inputs, browser steps, allowed domains, outputs, and success assertions.

name: hn_search
version: 1
risk: read_only
permissions:
  allowed_domains: [hn.algolia.com]
  submit_forms: false
inputs:
  query: { type: string, required: true }
steps:
  - { id: search, action: goto, url: "https://hn.algolia.com/?q={{query}}" }
outputs:
  results: { type: string }
success:
  - { id: results_present, assertion: output_not_empty, field: results }

A validator rejects undeclared actions, unauthorized domains, missing output assertions, changed manifests, and attempts to let page content change policy or tool metadata.

3. Execution model

  1. Parse and validate the workflow.
  2. Validate caller input and manifest digest.
  3. Apply runtime policy.
  4. Run declared steps in an isolated browser context.
  5. Evaluate assertions.
  6. Return typed output and provenance after writing a redacted trace.

The runner fails closed. Recovery may propose a patch, but it cannot silently modify or execute a workflow.

4. MCP mapping

Each valid workflow becomes one typed MCP tool. Its name, description, input schema, output schema, and permissions come from the reviewed contract. Invalid workflows are never exposed.

{
  "status": "success",
  "output": { "results": "..." },
  "provenance": {
    "workflow": "hn_search", "version": 1,
    "manifestDigest": "sha256:...", "runId": "run_..."
  }
}

5. Security and privacy

Page text, extracted values, tool descriptions, and tool outputs are untrusted data. Authorization comes from the validated workflow, caller identity, browser-profile policy, and runtime configuration, not from the model.

  • Explicit domain allowlists.
  • Isolated or labelled browser profiles.
  • Redacted credentials, cookies, tokens, and sensitive fields.
  • Human approval for writes, payments, uploads, messages, and destructive actions.
  • Auditable refusals and policy decisions.

6. Reliability and interoperability

Implementations should use stable selectors, bounded waits, assertions, failure categories, reproducible fixtures, and run metrics. When available, a first-party API or native WebMCP tool should be preferred over browser replay. WebMCP discovery and execution remain separate authorization decisions.

7. Conformance

Level 0: Contract. Typed parsing, validation, policy, and manifest digest.

Level 1: Replay. Read-only steps, assertions, traces, and provenance.

Level 2: MCP. Validated workflows exposed as structured MCP tools.

Level 3: Interoperability. Safe API, WebMCP, session, and bounded-recovery adapters.

8. Open questions

Open design areas include workflow portability, selector standards, signed distribution, remote profile isolation, a common trace format, native WebMCP authorization, and long-running MCP task handles.

Appendix: relationship to existing projects

Playwright MCP exposes generic browser-control tools. WebMCP lets websites expose native tools to browser-integrated agents. This proposal defines the authoring, validation, replay, governance, and provenance layer for external MCP tools based on reviewed browser workflows.
