Browser Workflow Tools for MCP

A draft contract and execution model for exposing a reviewed browser workflow as one narrow, typed Model Context Protocol tool. 

workflow contract -> validation -> policy check -> replay -> typed result

This is an early implementation-oriented proposal from the browser-to-mcp project. It is not a W3C Recommendation, an MCP specification, or an endorsement by either project.

1. Overview

Useful work often exists only behind a web interface. General browser controls can operate those interfaces, but recurring runs may need to plan against the page and select low-level actions again. A reviewed workflow makes the intended inputs, steps, permissions, outputs, and success conditions explicit before execution.

The result is a capability such as hn_search(query), rather than an unrestricted collection of click, type, and navigation controls. Improved reliability, cost, or safety is a testable hypothesis, not an assumption of this proposal.

Goals

  • Human-reviewable, versioned workflow definitions.
  • Typed MCP inputs and structured outputs.
  • Explicit domain, action, and side-effect policy.
  • Deterministic replay with success assertions.
  • Redacted traces and provenance for each invocation.
  • A clear relationship with first-party APIs and native WebMCP.
  • Evaluation rules that separate overhead from product value.

Non-goals

  • A new browser automation engine.
  • Unrestricted remote browser control.
  • Bypassing CAPTCHA, access controls, or site policy.
  • Automatic payments, messages, uploads, or destructive actions.
  • A public credential or workflow registry.

2. Workflow contract

The canonical authoring format is YAML. A workflow declares its identity, manifest, permissions, inputs, ordered steps, outputs, and success assertions. Implementations parse it into a strict typed model before a browser starts or an MCP tool is exposed. 

name: hn_search
description: Search Hacker News and return visible matching results.
version: 1
risk: read_only

manifest:
  version: 1

permissions:
  allowed_domains:
    - hn.algolia.com
  downloads: false
  uploads: false
  submit_forms: false
  send_messages: false
  spend_money: false
  requires_authentication: false

inputs:
  query:
    type: string
    required: true
    min_length: 1

steps:
  - id: search
    action: goto
    url: https://hn.algolia.com/?q={{query}}
    timeout_seconds: 30
    risk: read_only
    idempotency: safe
    retry: none
    confirmation: never
  - id: results
    action: extract_text
    selector: main
    timeout_seconds: 30
    risk: read_only
    idempotency: safe
    retry: none
    confirmation: never

outputs:
  results:
    type: string

success:
  - id: results_present
    assertion: output_not_empty
    field: results

The example is illustrative. A live workflow must declare every required origin and is rejected if it requests an unsupported action, leaves its allowlist, omits a required safety field, enables a disallowed side effect, references an undeclared output, or contains duplicate step or assertion identifiers.

Canonical manifest

The name, version, description, permissions, schemas, steps, and assertions form a canonical manifest. Its digest identifies the reviewed behavior and makes metadata changes visible.

3. Execution model

  1. Load and parse the workflow.
  2. Validate the typed contract and caller input.
  3. Check the manifest and runtime policy.
  4. Create an isolated browser context.
  5. Enforce domain and action policy before each step.
  6. Execute only the declared steps.
  7. Evaluate success assertions.
  8. Write a redacted trace.
  9. Return the typed result or a structured failure.

Validation, permission, assertion, and runtime failures stop the run. A recovery mechanism may propose a patch, but it cannot silently change and execute the reviewed workflow.

Integration priority

When corresponding adapters exist and are explicitly configured:

  1. First-party API.
  2. Native WebMCP tool.
  3. Deterministic browser replay.
  4. Bounded semantic recovery.
  5. Human review or a structured failure.

Discovery does not imply authorization. A page-provided tool is not safe merely because it is discoverable.

4. MCP mapping

Each valid workflow maps to one MCP tool. The reviewed workflow supplies the tool name and description, input schema, output schema, and policy boundary. Invalid workflows are not exposed. 

{
  "workflow": "hn_search",
  "manifest_digest": "sha256:...",
  "outputs": { "results": "..." },
  "trace_path": "traces/run_....json",
  "duration_seconds": 1.24
}

The implemented transport is local STDIO. Remote transport, authentication, and long-running task handling are separate deployment concerns and must not weaken workflow policy.

5. Security and privacy

The workflow contract is a security boundary. Page text, extracted values, tool descriptions, and tool outputs are untrusted data and cannot change permissions, schemas, or step targets.

  • Use explicit domain allowlists.
  • Isolate browser contexts unless a labelled profile is selected.
  • Redact credentials, tokens, cookies, and marked sensitive values.
  • Require separate review for writes and other side effects.
  • Record refusals and policy decisions for diagnosis.
  • Derive authorization from validated policy and runtime context.

6. Reliability

Browser workflows are sensitive to page changes, timing, authentication, localization, and anti-automation controls. Implementations should use stable selectors, bounded waits and retries, assertions, structured failure categories, controlled fixtures, and run metrics.

Provider-specific capabilities must be declared. A workflow should not silently gain behavior when moved between browser providers.

7. Evaluation and claims

Evaluation is split into four suites because each answers a different question.

SuiteQuestion
Runtime parityDo direct, workflow, and MCP paths preserve execution, and what overhead does each layer add?
Product valueDoes the same frozen model perform recurring work better with generic Playwright MCP tools or a generated workflow tool?
SafetyDoes useful work complete without violating declared policy?
ResilienceHow does the runtime behave under controlled page, network, schema, and protocol faults?

The existing Direct, Workflow, and MCP paths all use Playwright. Their comparison is an internal parity and overhead study, not a competitive benchmark against Playwright or Playwright MCP.

A product comparison keeps the model, prompt, task state, validator, budgets, browser, and network condition fixed. It reports Completion Under Policy, turns, tokens, tool calls, browser actions, duration, cost, invalid calls, violations, structured-result validity, provenance, and diagnosis quality. Workflow preparation and maintenance cost must be reported with recurring execution cost.

Claims must state the task set, run count, environment, date range, model when used, and denominator. Results from a small task set cannot be generalized to arbitrary websites.

8. Conformance

Level 0: Contract. Typed parsing, validation, policy, and manifest digest.

Level 1: Replay. Read-only steps, assertions, traces, and provenance.

Level 2: MCP. Validated workflows exposed as structured MCP tools.

Level 3: Interoperability. Safe API, WebMCP, session, and bounded-recovery adapters.

An implementation must state its level and unsupported actions. The current reference implementation targets Level 2. Read-only native WebMCP discovery is not, by itself, a Level 3 claim.

9. Current status

The reference implementation supports strict YAML contracts, local read-only replay through Playwright, generated MCP tools over STDIO, structured results, domain policy, assertions, redacted traces, failure screenshots, and deterministic readiness fixtures. It also records native WebMCP metadata without invoking discovered tools.

Native WebMCP execution, authenticated workflows, writes, existing-tab attachment, hosted browsers, remote transport, and automatic recovery are not implemented. Hacker News and Wikipedia search are current example workflows, not evidence of broad website coverage.

Next evidence milestone

Run a paired study in which the same frozen model receives either generic Playwright MCP tools or one generated workflow tool for the same controlled task. Evaluate safety and operational resilience separately before making product or marketing claims.

10. Open questions

  • Workflow and locator portability between browser providers.
  • Remote workflow distribution and signing.
  • Profile isolation and authorization for authenticated execution.
  • A common trace and evaluation record.
  • Authorization and representation of native WebMCP execution.
  • Long-running MCP task handling.
  • Portable accounting for preparation and maintenance cost.
